# Independent review of the Day 7 close-out

Reviewed November 2, 2026 (Europe/London), starting at clean `0096e05`. Scope: D52/D53 and the changes since `4f974e4`, current source/tests, generated evidence, CI, and the production browser. This is a review, not a repair or a release approval. Findings below remain open.

Confidence: **[Certain]** means directly observed code, output or browser behaviour; **[Likely]** means an inference or recommendation.

## Verdict

**[Certain]** The implementation work is real, and the reported offline test counts are reproducible. The statement “none degrading” is too strong: the new brush snapping can discard most of the area the user selected for privacy masking. Two original recommendations are also only partly resolved: uncertainty styling disappears when SAM supplies an outline, and result selection still has ambiguous same-day ties.

**[Likely]** Keep the feature scope frozen. Repair the privacy defect first, fix the narrow rendering/publication defects, correct evidence wording, and finish human-use and release checks. More models or interface redesign would dilute the remaining work.

## 1. Findings, in priority order

### A — P1: brush snapping can reduce the user's privacy selection

**[Certain]** `apps/web/app/app/page.tsx:289` computes the drag rectangle, but lines 293–295 replace it with the bounds of touched OCR lines whenever any line intersects. Content inside the drag but outside those OCR bounds is no longer masked.

Production reproduction on the bundled synthetic billing image:

- Drag rectangle: left 14%, top 30%, width 26%, height 5% of the image.
- Final mask: left 15.8594%, top 31.5%, width 5%, height 1.375%.
- The resulting mask covers the detected name, not the full selected area.

**[Likely]** If the drag also covers an OCR-missed address fragment, identifier or non-text detail, those selected pixels can remain in the upload. This conflicts with the brush's privacy role (FLOW-3, PRIV-1/2; R3). The review still shows the smaller mask, so this is not proof that real personal data leaked during this audit; only synthetic data was used.

**[Likely]** Preserve the entire drag rectangle and expand it to include touched OCR bounds. A regression must assert pixel coverage/rectangle containment, not merely that the number of masks increased. Include mixed detected and missed content, and touch input.

### B — P1 for evidence integrity: negatives dev/held-out boundaries overlap

**[Certain]** `eval/showme_eval/cli.py:135` builds dev negatives from the dev partition; line 141 builds the “heldout” negatives from the complete v2 dataset. It does not exclude dev sources.

Comparing the committed v3 prediction files using `(image_sha256, instruction)` gives:

- One identical image/goal pair in both negatives-dev and negatives-heldout: held-out `neg-61`, “sort from largest to smallest”.
- 63 shared image hashes and 99 shared goal texts between the negative suites.
- 101 of the first 200 headline negative rows use a goal found in the original v2 dev partition.

**[Certain]** The ordinary v2 split is by annotation/sample, not screenshot: dev and held-out share 63 images but no identical image/instruction pairs. Shared images alone do not establish an incorrect score; the exact negative-pair overlap is the direct failure of isolation.

**[Likely]** The recorded 161/210 arithmetic remains valid for those recorded probes, but “independent held-out honesty” is too strong. Fix the selection boundary, save an immutable split manifest, and add disjointness assertions for generated image/goal pairs; prefer image/group separation for a future generalization claim. Disclose the existing overlap before submitting. Do not tune on the corrected reporting set.

**[Certain]** There is a second reporting distinction: 161/210 combines 151/200 mismatched absent-target pairs with 10/10 synthetic injection probes. The generated negative report already separates these. Public copy calls the aggregate absent-target honesty without exposing that composition. Preserve the three breakdowns: absent pairs 151/200 (75.5%), injection 10/10, refusals 12/12. No generated output was edited in this review.

### C — P2: publication selection still cannot resolve equal-size runs on the same date

**[Certain]** `apps/web/scripts/gen-results.mjs` sorts benchmark candidates by sample count and date only. The added regression uses different dates. In an isolated fixture with equal n=1172 and date 2026-11-02, an earlier v2 row followed by a later v3 row published v2's 90.7%, not v3's 89.9%.

**[Certain]** Current production headlines are the intended v3 runs and the new SHA-tagged E2E run. The E2E directory priority fix works for the reported historical failure.

**[Likely]** Use an explicit publication manifest for the frozen model/prompt/split/config, or persist a full creation timestamp and enforce those filters. A random run suffix or date-only tie is not evidence of recency. Add a same-day equal-n regression. The negatives headline selector should explicitly require the reporting split as well.

### D — P2: an unsure SAM outline becomes solid

**[Certain]** `apps/web/components/Overlay.tsx:28` removes the dashed box when an outline exists. The three SAM paths at lines 31–33 have no `strokeDasharray`. The question-mark badge and uncertainty text remain, so uncertainty is not completely erased, but FLOW-7's dashed treatment is lost.

**[Certain]** This reproduced both by rendering the actual component and through a temporary synthetic production guide: status/caution survived the API round-trip; the viewer showed the warning, question mark and uncertainty copy, but contained zero dashed elements. The fixture was deleted successfully and the next API read returned 404.

**[Likely]** Apply the unsure dash pattern to the outline strokes and test unsure plus SAM in both `/app` and `/g`. The existing FLOW-7 test uses a box fallback; the new guide regression tests API persistence, not recipient rendering.

**[Certain]** A related robustness gap is `GuideStepper.tsx:13`: any targetless step becomes `done` in its rendering shim, even if the stored status says `unsure` or `not_visible`. An unsure targetless fixture retained its caution but lost its uncertainty banner. Normal post-processing supplies a target for unsure; treat this as a contract/backwards-compatibility edge case, not proof that every ordinary guide is affected. The guide also does not preserve separate `scroll_direction`/`type_text` fields.

### E — P2 security readiness: unsupported framework and unresolved dependency advisories

**[Certain]** `pnpm audit --prod --json` reports 29 advisories for the locked production dependency tree: 3 critical, 11 high, 13 moderate, 2 low. The installed Next.js version is 14.2.35. The [official support policy](https://nextjs.org/support-policy) lists 14.x as unsupported.

**[Certain]** These are dependency-range matches, not 29 demonstrated exploits. For example, the [SVG optimizer advisory](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw) has an upstream image-library/hosting condition and a `sharp` workaround. The [Server Actions DoS advisory](https://github.com/vercel/next.js/security/advisories/GHSA-p3m5-59mp-jv5r) requires at least one Server Action. This source uses ordinary `<img>` elements and no `use server` declarations were found. No exploit probes were sent to production.

**[Likely]** Triage applicability and hosting mitigations, then move to a supported patched release in a tested branch. Do not call this a completed security pass or blindly run an automatic force-upgrade. CI currently checks secrets and tests but does not gate dependency advisories.

### F — P2 evidence provenance and documentation remain incomplete

**[Certain]** All three v3 headline summaries record git SHA `4f974e4`, whose committed prompt is v2. Their per-prediction prompt label is v3. This is consistent with running against uncommitted changes, but the report records neither a dirty-tree flag nor a prompt/source fingerprint. It cannot independently identify the exact evaluated source by SHA alone.

**[Certain]** Production metadata also says `bb543ba` with `gitDirty=1`. A direct source-manifest comparison resolves the runtime concern for this audit: 39 backend files match local SHA-1 contents; 80 web files match; the sole differing tracked web file is the later `playwright.config.ts` worker change. `.gitignore` files are absent from deployment, as expected. Runtime source matches current local code despite the weaker deployment metadata.

**[Likely]** Future reports should require clean source or store a dirty flag plus source/prompt digest. Publish an explicit evidence-to-release mapping; never rewrite old generated summaries to invent provenance. Close-out docs still cite older E2E counts, “all M green” despite PRIV-11, and an outdated demo script in DESIGN.md. The updated three-minute script in SUBMISSION.md is the better current plan.
