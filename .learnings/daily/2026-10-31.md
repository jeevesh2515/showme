## How a share request flows

1. User finishes a task → taps "Share these steps".
2. App shows each redacted step picture again; user ticks each picture + the consent box.
3. Browser sends the pictures to `POST /v1/guides` (only redacted images ever leave the device).
4. Backend checks consent, charges the 5-per-day share quota, stores pictures in the private bucket and a record holding only hashes of the token and delete key.
5. User gets a link (`/g/<token>`) and a one-time delete key, kept only in that tab.
6. A visitor opening the link gets the steps with picture URLs that expire in 10 minutes; after 7 days every read returns "gone" and the daily purge deletes the files.
7. "Delete now" sends the delete key in a header; wrong key = refused, right key = pictures deleted first, then the record.

## 5 likely judge/interviewer questions

1. "How do shared guides stay private?" — Opt-in only, second review of every picture, 128-bit token stored only as a hash, private bucket with 10-minute signed URLs, 7-day expiry checked on every read, delete key, noindex headers. Verified locally; live Supabase check pending my project creation.
2. "What did your security review actually find?" — That our cron job used the wrong HTTP method so expired guides would never be deleted, picture URLs were missing a path segment, and the consent flag was hardcoded in the client. All fixed with regression tests; final score 8.6/10.
3. "Your E2E says 1/10 — is the product bad?" — That run measured a rate-limiter bug (fixed same day) plus two genuinely hard tasks. The benchmark numbers (90.7% ScreenSpot-v2) are the accuracy evidence; the E2E re-run after deploy is the task-level evidence, and we publish both either way.
4. "Is it accessible?" — axe reports 0 violations on every screen; text size to 150%, high contrast, full keyboard operation, screen-reader announcements, 48px targets — all covered by automated tests. A human VoiceOver pass is still on my list.
5. "What stops someone abusing the public demo?" — Per-IP hourly/daily step limits and a $5/day, $60 total spend cap, now stored in Supabase so they hold across server instances; production refuses to boot without them.
